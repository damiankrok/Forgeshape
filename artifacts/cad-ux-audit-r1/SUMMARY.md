**Baseline:** `42314cbfece5a27f163045f090394603ab80246b` · worktree clean at start
and at finish · no remote · **no product, runtime, test, schema or fixture

---

## The verdict in one paragraph

The domain is in better shape for this than the UI suggests. A CAD Body's truth
is already **one retained sketch plus one extrusion that references a profile by
id and copies no geometry**; the sketch survives Extrude, is stored in `CADB`, is
snapshotted whole by the history and is reopenable through a staged Edit Sketch
that already writes into an existing body as one transaction. What is genuinely
missing splits into three very unequal pieces: an in-viewport control of any kind
(there is none — depth and direction live only as fields and chips in a side
panel); an extent model beyond a two-valued direction (which needs bytes but
**not** a boolean kernel, because `generateCadMesh` already spans two independent
offsets); and Add/Cut on the same body (which needs both a boolean kernel **and**
turning `CadBodyState` from a deliberate struct into an ordered feature list —
and the second is the larger change).

## Five findings that should shape the coordinator's decision

**1. The retained-sketch requirement is already met below JNI; the gap is UI.**
`CadBodyState = CadSketch + ExtrudeFeature` (`forgeshape_cad_body.h:86`), the
extrusion names a profile by `SketchEntityId`, and everything drawn is
regenerated by `generateCadMesh`. Nothing consumes the sketch. The sketch is
simply not *findable*: the only route is select body → precision surface → scroll
→ `Edit Sketch`, and nothing anywhere indicates a body has a sketch at all.
**Zero schema impact to fix.**

**2. Symmetric and Two Sides A/B do not need the kernel, and they are the biggest
kernel-free win available.** `generateCadMesh` already builds between
`nearOffset` and `farOffset` (`forgeshape_cad_body.cpp:108-111`); direction only
decides which one is zero. What is missing is *storage* — a `CADB` **v4** with an
extent code and a second distance, written only when used, leaving all 30
existing fixtures byte-identical.

**3. "Same logical body Add/Cut" is a feature-list problem first and a boolean
problem second.** `CadBodyState` is a struct on purpose — the header says so:
*"a struct rather than a list so nothing pretends a feature tree exists; when a
second feature kind arrives it takes a new `CADB` section version rather than a
discriminator inside this one."* Making it a list touches the domain, the
history's boundedness guarantee, the codec, `DATA_PACKAGE_SPEC.md` and the
PowerShell corpus builder. The boolean itself touches one function. A one-feature
list can be made to encode byte-identically to v3, which is the migration plan.

**4. There is a trap the coordinator should see named.** Sketching on a CAD
body's planar face already produces a body that *follows* its producer through
`resolveWorldModel`. It looks a great deal like Add. It is two bodies, two `CADB`
records, two Objects rows and no boolean, and presenting it as Add would be
exactly the hidden-`SceneObject` workaround the contract forbids.

**5. Every mechanism the canvas UI needs already exists and is proven twice.**
`SketchOverlayPtr` has three producers already and the renderer draws whatever it
is handed, last, depth-off — so an extrusion arrow costs no renderer change.
World-anchored numeric chrome is the `BodyDimensionLabelAnchors` →
`bodyDimensionLabelPoint` → `BodyDimensionLabelsView` pattern, done twice.
`projectWorldToScreen` and `worldMetersPerPixel` are public platform-neutral
helpers. And `PointerToolType::Mouse` is already in the neutral input wire.

## The one thing that must be built new rather than reused

The gizmo's camera-derived scale produces a **constant screen size** — correct
for a placement instrument, and the opposite of what the owner asked for. The
extrude cluster wants a world reference size clamped into a screen band:
`S = clamp(W / worldMetersPerPixel, S_min, S_max)`, drawn and hit-tested at
`s = S · worldMetersPerPixel`. That is a small new pure function *beside* the
gizmo's, sharing its primitive, and its constants are deliberately **not** chosen
in this audit — they are a feel decision for the owner, put with screenshots at
three zoom distances, the way `SCULPT-FCM-R1` handled its two feel constants.

## Cross-platform seam

The line is already where it should be. `EditorUiState` is an explicitly closed
list of what Java may remember — *"drafts, presentation and layout"* — and no CAD
semantics live above JNI. Two things to fix while building: `draftDirection`, an
extrude field currently held as an `int` in **two** Java views (harmless at one
field, exactly the wrong seed for operation + target + two distances), and the
absence of any neutral vocabulary for hover, wheel, right-click and modifiers —
`TouchAction` has six values and none of them is Hover or Wheel. Neither blocks
the Android work; both should be recorded before a desktop adapter is attempted.

```
canvas UI        Symmetric/         a kernel        feature list      boolean
for what         Two Sides A/B      decision        + Add/Cut         topology
already          (CADB v4)                          (CADB v5)
exists
(no bytes)
```

Working names only. If exactly one stage is authorized, it should be
**`CAD-UX-S1`**: it converts an already-correct domain into the canvas-first
interaction the owner described, it is the surface every later stage plugs into,
and it changes not one persisted byte — reverting it in full would leave every
`.forge` file identical.

## What this audit could not settle

* `GATE-KERNEL`, `Stage024`, `CAD-A4` and `OQ-A` **do not exist anywhere in the
  repository** — grep over all Markdown found zero occurrences. They are treated
  as the coordinator's own labels. The nearest recorded owner decision is
  `UI-OWNER-04`: *"the first Extrude vertical slice supports New Body; Extrude
  Add and Cut are required integration after boolean infrastructure exists."*
* Which boolean kernel, under which licence. The repo bans third-party runtime,
  rendering, math and input libraries; a geometry kernel is a new category and
  needs its own explicit owner decision, including a **determinism** contract —
  `.forge` stores no vertex, so a non-deterministic kernel would make a reopened
  project a different project.
* Final screen-scale constants, the occlusion policy for a Cut preview, and the
  `CapPlane` naming consequence once neither cap lies on the sketch plane. All
  three are recorded as owner questions, not answered.
