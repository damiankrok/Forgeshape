# CURRENT_FLOW — how a sketch becomes a body today

**Task:** `CAD-UX-AUDIT-R1` · **Baseline:** `42314cbfece5a27f163045f090394603ab80246b`
**Status:** audit only. No runtime, test, schema or fixture change.

Every claim below is a file and a line in the baseline tree. Where this document
says "does not exist", it means a grep over `app/src/main/cpp`,
`app/src/main/java` and `app/src/main/res` found no such thing.

---

## 0. The one-paragraph answer

A CAD Body's authored truth is **one sketch and one linear extrusion**, held in
`CadBodyState` (`forgeshape_cad_body.h:86`). The sketch is **retained** — it is
the body's truth, not a consumed input, and the extrusion **references** a
profile by entity id rather than copying geometry. Everything drawn is
regenerated by `generateCadMesh`. So the "retained, reusable sketch" the owner
asks for is already true *below JNI*; what is missing is (a) an access path to
it that is not two levels deep in a panel, (b) any notion of a second feature,
an operation or a target body, and (c) any in-viewport control at all — depth
and direction exist **only** as fields and chips in a side panel.

## 4. Flow C — Extrude New Body: exactly where a body is minted

**One place mints a `SceneObject` for an extrusion in an open project:**

```
forgeshape_sketch_session.cpp:1087-1094
    ScopedConstructionEdit edit(history);          // one transaction
    body = scene.addCadBody(state, &why);          // <-- the mint
    if (body != nullptr) publishSceneObject(*body);
```

`ConstructionScene::addCadBody` (`forgeshape_scene.h:444`) regenerates the mesh
**once before the id is minted**, so a refusal costs no `ObjectId`. It appends
the body and makes it active. `SceneObject`'s CAD constructor
(`forgeshape_scene.h:97-101`) fixes `BodyRepresentation::Cad` for the life of
the object.

**The other mint** is the bootstrap: `commitFirstCadProject`
(`forgeshape_project_bootstrap.h:70`), which does not call `addCadBody` at all —
it builds a document and loads it. There are exactly these two.

`generateCadMesh` builds the solid between two offsets:

```
forgeshape_cad_body.cpp:108-111
    nearOffset = (direction == AlongNormal) ? 0.0 : -depth;
    farOffset  = nearOffset + depth;
```

so the geometry generator is **already two-sided in shape** — direction only
decides which cap sits at offset 0.

**This is the existence proof that a sketch commit need not mint a body.** The
codebase already contains a commit path that writes into an existing body as one
transaction. What it does not contain is a commit that *combines* new geometry
with what the body already has.

## 6. Where the user can and cannot find a sketch again

| Question | Answer in the baseline |
| --- | --- |
| Is the sketch still truth after Extrude? | **Yes.** `CadBody::sketch()` (`forgeshape_cad_body.h:137`) returns it; `CADB` stores it; a history step copies it (`forgeshape_history.h:86`). |
| Is it listed anywhere? | **No.** Grep found no sketch row, feature row, timeline or history browser. `ObjectsSectionView` lists bodies only. |
| How many taps to reach it? | Select body → open precision surface → `Edit Sketch`. Three, and the last one is below the depth/direction fields in a scrolling panel. |
| Can two bodies share one sketch? | **No.** `CadBodyState` embeds a `CadSketch` **by value** (`forgeshape_cad_body.h:87`). There is no sketch identity outside a body and no way to name one. |
| Can one sketch feed two features? | **No.** `CadBodyState::extrude` is a single `ExtrudeFeature`, not a list. The header states this is deliberate: *"a struct rather than a list so nothing pretends a feature tree exists"* (`forgeshape_cad_body.h:39-42`). |

## 7. What the extrusion currently carries

```cpp
// forgeshape_cad_body.h:73-79
struct ExtrudeFeature {
    SketchEntityId  profileEntityId = kNoSketchEntity;  // a reference, not geometry
    Meters          depth           = 1.0;
    ExtrudeDirection direction      = AlongNormal | AgainstNormal;   // exactly two
};
```

Absent, at every layer (domain, history, JNI, codec, UI): an **operation**
(Add / Cut / Intersect / New Body), a **target body**, a **second distance**, a
**symmetric** flag, and any **extent mode** beyond the two-valued direction.
`CadStatus` (`forgeshape_sketch.h:57-125`, 31 values) has no refusal that names
one either.

## 8. Where a sketch and a CAD Body reach the renderer

* A committed CAD Body: `publishSceneObject` → `MeshStore` → `RuntimeMesh` →
  `buildRenderMesh` → one shaded draw per body. Identical to a primitive; the
  renderer cannot tell them apart.
* A sketch in progress: `SketchSession::overlay(worldPerUnit)` →
  `SketchOverlayPtr` (world-space `GizmoVertex` line list plus styled ranges,
  `forgeshape_sketch_overlay.h`) → uploaded on the gizmo's line pipeline →
  recorded **last** in the main pass (`forgeshape_renderer.cpp:3416-3420`),
  depth-test off, depth-write off.
* Two other producers already emit the same `SketchOverlayPtr` type:
  `SupportChooser::overlay()` and `buildBodyDimensionOverlay`
  (`forgeshape_body_dimension_overlay.h:60`). **A third producer is a proven,
  zero-renderer-change pattern.**

## 11. Transaction and persistence at the end of every flow

* One user act = one `ScopedConstructionEdit` = at most one history step. A
  commit that finds nothing different records nothing and leaves redo alone
  (`forgeshape_history.h:158-172`).
* A history step holds the **whole** `CadBodyState` per CAD body
  (`forgeshape_history.h:80-86`) — bounded by `kMaxSketchEntities` (256) and
  `kMaxPolylineVertices` (256). No vertex, ever.
* `CADB` is written at the lowest version that can express the project: v1 for a
  world-plane, straight-edge CAD project; v2 when any body is face-supported;
  v3 when any sketch carries an Arc or a Spline, and v3 always writes the v2
  block (`DATA_PACKAGE_SPEC.md:569-583`).
