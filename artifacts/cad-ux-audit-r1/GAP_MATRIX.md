Working stage names below (`CAD-UX-S1`, `CAD-EXT-R1`, …) are **proposals for the
coordinator**, not authorized ids. `GATE-KERNEL`, `Stage024` and `CAD-A4` are the
prompt's own labels; **no such identifier exists anywhere in the repository** —
grep over all Markdown found zero occurrences. The nearest recorded owner
decision is `UI-OWNER-04` (`PROJECT_STATUS.md:1810-1817`): *"The first Extrude
vertical slice supports New Body; Extrude Add and Cut are required integration

volatile session, `JNI` = adapter, `REN` = renderer/overlay, `UI` = Android
shell, `FMT` = `.forge` codec + spec + corpus script.

## 2. Secondary findings the coordinator should see

| # | Finding | Why it matters | Source |
| --- | --- | --- | --- |
| S1 | **A face-supported sketch is not "Add", and must never be shown as one.** Sketching on body A's face creates body **B**, which *follows* A through `resolveWorldModel` composing `producerWorldModel · faceFrame`. Two bodies, two `CADB` records, two Objects rows, no boolean. | Visually this is very close to what the owner wants Add to look like. Presenting it as Add would be precisely the "hidden SceneObject workaround" the prompt forbids. | `scene.h:392`; `ARCHITECTURE.md:2370-2378` |
| S2 | **Add/Cut merging a dependent into its producer would change two existing refusals.** Deleting a producer with dependents is refused (`RefusedHasDependents`) and duplicating a face-supported CAD body is refused (`RefusedFaceSupportedCad`). If a later feature absorbs a dependent, both refusals cover a case that no longer exists in the same shape. | These are owner-approved behaviours today (Stage 018A, `UI-OWNER-45`). Any Stage024 design must say what happens to them. | `CLAUDE.md`; `forgeshape_body_commands.h` |
| S3 | **The feature-list change is bigger than the kernel change.** `CadBodyState` is a plain struct compared bit-exactly by `sameCadBodyState`, copied wholesale into every history step, and encoded field-by-field by the codec **and** re-implemented by `scripts/build-forge-corpus.ps1`. Making it a list touches all four. The boolean itself touches `generateCadMesh` and nothing else. | Sequencing the kernel first and the model second would leave a kernel with nothing to drive it. Sequencing the model first is possible *only* if a one-element list is byte-identical to v3 — which is a real design option worth stating. | `cad_body.h:88-96`; `history.h:86`; `DATA_PACKAGE_SPEC.md:433-490` |
| S4 | **`generateCadMesh` is already two-sided in shape.** `nearOffset`/`farOffset` are two independent doubles; direction only decides which one is 0. Symmetric and Two-Sides are a storage-and-UI stage, not a geometry stage. | This is the largest CAD UX win available with **no** kernel dependency. | `cad_body.cpp:108-111` |
| S5 | **A third `SketchOverlay` producer costs the renderer nothing.** `SketchSession`, `SupportChooser` and `buildBodyDimensionOverlay` all already produce `SketchOverlayPtr`; the renderer draws whatever it is handed, last, depth-off. | An extrusion arrow and its ticks are a line list. No new pipeline, no new pass, no push-constant slot. | `sketch_overlay.h`; `renderer.cpp:3416-3420` |
| S6 | **`CadStatus` is a single closed enum of 31 values, mirrored as `CAD_*` ints in Java and used by the codec's refusal table.** Every new refusal (`InvalidExtent`, `NoTargetBody`, `BooleanFailed`, …) is a coordinated three-place change. | Cheap, but it is not a one-file change and it is easy to miss the Java mirror. | `sketch.h:57-127`; `NativeViewport.java:2152-2182` |
| S7 | **Overlay controls are depth-test-off / depth-write-off and drawn last.** An extrusion manipulator inherits "always on top of the model" for free. Whether that is right for a control that must communicate *inside* a solid (Cut) is an owner question, not a default. | Occlusion policy must be decided deliberately, not inherited. | `renderer.cpp:3411-3420` |
| S8 | **The sketch owns the single-finger gesture while open; two fingers still pan and pinch.** Any in-viewport extrude manipulator lands in the same arbitration and must state whether it takes the single finger from the sketch, from the camera, or only in the `Ready` state. | `Ready` is the natural home: the drawing is finished, so the single finger is free. | `CLAUDE.md` CAD rule; `sketch_session.h:311-318` |
